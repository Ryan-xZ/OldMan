# 老头乐 · 版本发布规范

> 本规范约束每一次新版本推送的**版本号、Release 标题、更新说明正文、推送内容与流程**，
> 供技术员与 AI 助手共同遵循，保证各版本发布风格统一、信息可比、内容安全。
> 遵循本规范本身即是要求：本文档的层级、用语也按此标准书写。

## 1. 适用范围

- 适用对象：向本仓库发布 Release 的所有人员与自动化脚本（含 `scripts/release.ps1`）。
- 单一数据源：更新说明内容以 `Changelog.kt` 对应版本条目为准，`release.ps1` 自动提取，**不要在多处各写一份**。

## 2. 版本号规范

采用语义化版本，`versionName = 主.次.修订`，`versionCode` 为单调递增整数。

| 位置 | 递增条件 | 示例 |
| --- | --- | --- |
| 主版本 | 重大重构或不兼容改动 | `2.0.0` |
| 次版本 | 新增功能、较大优化 | `1.6.0` |
| 修订版本 | 缺陷修复、文案微调 | `1.6.1` |

规则：
- `versionCode` 每次发布 **+1**，且 `Changelog.kt` 条目的 `code` 必须与之一致。
- Git 标签固定格式 `vX.Y.Z`（小写 `v` 前缀，与 `versionName` 完全一致）。
- 预发布版在版本号后加 `-betaN`（如 `1.6.0-beta1`），仅用于内部验证，正式版必须去掉后缀。

## 3. Release 标题规范

- 格式固定为：`老头乐 X.Y.Z`
- 不加日期、不加 emoji、不加"发布/新版本"等冗余词；日期由 GitHub Release 自带展示。
- 预发布版标题追加 `（预发布）`：`老头乐 1.6.0-beta1（预发布）`。

## 4. 更新说明正文规范

正文为**纯文本 Markdown 列表**（App 内更新弹窗按纯文本渲染，勿使用 HTML、图片、徽章或外链头图）。

### 4.1 分类与前缀
每条以统一分类词开头，顺序按"新增 → 优化 → 修复 → 其他"，同类按重要性由高到低：

| 分类 | 使用场景 |
| --- | --- |
| `新增` | 全新功能或入口 |
| `优化` | 已有功能的体验、性能、界面改进 |
| `修复` | 缺陷、崩溃、兼容性问题 |
| `调整` | 交互、文案、默认值等非功能性变更 |
| `移除` | 删除某功能或入口 |

### 4.2 书写要求
- 每条**一句话**，建议 ≤ 30 字，最多不超过 40 字；一个要点一行，不合并多件事。
- 以动词或功能名词开头，直接说明"做了什么 / 对用户的影响"，不用"更好地""极大地"等空洞修饰。
- 不写实现细节、内部模块名、接口地址；面向用户可感知的变化。
- 使用中文标点；功能名、页面名与 App 内文案一致（如"自动工具""排班""B站助手"）。
- 不使用第一人称、不致谢、不预告未来版本。

### 4.3 示例
正例：
```
新增 GitHub 应用内更新：自动检测新版本并支持镜像加速下载
优化排班日历：默认选中下个月，删除按钮跟随所选月份
修复 B站经验页投币数量显示错误
```
反例：
```
新增了对 update 模块中 GithubUpdateChecker.fetchLatestRelease 的重构（暴露实现细节）
优化了很多体验，感谢大家支持（空洞、致谢）
修复 bug（过于笼统，看不出修了什么）
```

## 5. 推送内容规范（硬性限定）

- **只推送**：签名 release APK 与文档（README/docs）。
- **禁止推送**：任何源码、`local.properties`、签名密钥库、密钥口令、`.git` 凭据。
- APK 命名固定：`OldMan-vX.Y.Z.apk`；每个 Release **仅一个 APK 资产**。
- APK 必须为 `assembleRelease` 的**已签名**产物；未签名包不得发布。
- 更新说明正文不得包含：Token、密钥、内网/私有地址、他人隐私、可绕过安全机制的具体细节。
- 大文件、二进制、日志、抓包数据一律不入库。

## 6. 发布流程

1. 在 `build.gradle.kts` 递增 `versionName` 与 `versionCode`。
2. 在 `Changelog.kt` **列表头部**新增对应版本条目，`code` 与新 `versionCode` 一致，bullets 按第 4 节规范书写。
3. 本地自测通过（安装、核心功能、更新检查）。
4. 执行 `scripts/release.ps1`（预发布加 `-Prerelease`）。
5. 校验发布结果：匿名访问 `releases/latest` 版本号、标题、说明、APK 资产均正确。

## 7. 禁止事项

- 禁止跳过 `Changelog.kt` 直接在 GitHub 网页手写发布说明（会造成数据源不一致）。
- 禁止同版本号重复发布不同内容；如需修正必须递增版本号。
- 禁止改动已发布 Release 的 tag 指向（除非由 `release.ps1` 统一处理）。
- 禁止向本发布仓库提交源码或任何敏感信息。
